1. Medium impact, high confidence: remove the superseded NVIDIA sandbox symlink workaround.
Locations: devices/nixos-desktop/hardware.nix:47-63, especially line50 and line62; hardware.graphics.enable at line30.
The local code reaches into systemd.tmpfiles.settings.graphics-driver to obtain the target of /run/opengl-driver and manually adds it to programs.nix-required-mounts.allowedPatterns.nvidia-gpu.paths. Pinned upstream already includes /run/opengl-driver in its defaults and sets unsafeFollowSymlinks=true (nixos/modules/programs/nix-required-mounts.nix:54-69). The hook discovers its target at build time. This can be reduced to:
  programs.nix-required-mounts = {
    enable = true;
    presets.nvidia-gpu.enable = true;
  };
This removes dependence on an internal tmpfiles record and 17 lines of obsolete explanation. Upstream already defaults hardware.graphics.enable=true when that preset is enabled (module line149), so desktop's explicit graphics.enable is also value-redundant, although retaining it as a declared host capability is reasonable.
Historical evidence: Connor Baker's 2025-07-18 commit 0b47ed1b35e2a894f4ace1d2280220fca4a9ad2c added the direct target upstream. On 2026-02-12, 02b74722d86f55b367011ac4b9ebafe7ffcbb11c removed the reference, enabled symlink following, and added an evaluation regression test because direct access could cause infinite recursion with userborn. On 2026-02-08, 867b4878b711adce951ee21e5e0bdc30039d6e80 made the GPU preset enable graphics by default. On 2026-03-16, 7a9bf2776062731e82a6bf0a6b41fdcdf44623a5 expanded following to descendant symlink targets and added tests.
Validation performed: imported the pinned Python hook with an already-installed Python interpreter; called mount_closure for actual /run/opengl-driver, with unsafeFollowSymlinks=true and safePrefixes=[/nix/store], once with and once without the explicit target. The discovered target was present and both returned exactly the same three mounts. No build or GPU test was executed.

3. Medium maintenance impact, high confidence: factor the entire repeated Disko dataset layout into the existing pure helper.
Locations: devices/nixos-build01/disko.nix:39; devices/nixos-desktop/disko.nix:40; devices/nixos-ext/disko.nix:42; devices/nixos-orin/disko.nix:30; util.nix:4.
The repeated zpool.rpool.datasets definitions have the same root snapshot hook and /nix, /tmp, /home, /persist layout; roughly 30-40 lines are repeated per host. util.nix already factors boot/rpool partitions, drive ID assembly, and ZFS properties. Move datasets into a shared zfsRpoolConfig or zfsRpoolDatasets helper and leave only disk serial/model/interface inventory in each host. Preserve the root@blank hook, all properties, device IDs, partition sizes, and disk membership exactly; filesystem-policy changes belong in a separate review. The standard NixOS module system can merge disko.devices.zpool.rpool pieces, so a common module is also reasonable. Prefer one reusable module/helper over four content generators or a filesystem DSL. README.md:13 already identifies this unfinished cleanup.

4. Medium maintenance impact: move the existing lightweight machine inventory out of the Nix tuning module.
Locations: modules/nix/default.nix:59-88 and :97-100; flake.nix:231-263; users/connorbaker.nix:78-82; modules/services/tribuchet.nix:8 and :40; devices/*/hardware.nix's three IPv4/MAC records; modules/services/prometheus-scrape-config.yaml's repeated instance names.
Architecture, host name, SSH public-key path, IPv4 address, build features, and builder role recur in several independent maps. A pure inventory.nix (values only, no nixosConfigurations evaluation) can feed these consumers. The existing comment at modules/nix/default.nix:26 correctly avoids forcing every system closure: preserve that property. Keep external spark-ee4c as a separate non-NixOS record. Encode hub role/address once instead of deriving role from the spelling of networking.hostName. An ordinary explicit per-host 'isHub' or role option is preferable to a general role engine. Keep disk serials and hardware workaround values close to their hosts, where they are easy to inspect.
This pays off when adding, renaming, or taking a builder offline, rather than promising an immediate speed improvement. Existing hardware network semantics require the separate networking audit before generating those records.

9. Optional medium complexity: share pkgs between compatible NixOS outputs using readOnlyPkgs, after measuring evaluation cost.
Locations: flake.nix:124-132 and :211-227.
The flake explicitly memoizes perSystem package sets, but each nixosSystem independently imports its own merged nixpkgs config. Upstream nixosModules.readOnlyPkgs exists to accept a prepared nixpkgs.pkgs set, prevent accidental module mutation, and reuse it across systems. It could share build01/ext's ordinary x86 package set with the perSystem tools. It is NOT a drop-in global rewrite: desktop retains cudaCapabilities=[8.9]; Orin's Jetpack module injects overlays and CUDA config and changes host/kernel selection. Either use named package variants for desktop or leave it module-instantiated. Preserve Orin's existing instance unless moving all Jetpack overlays/config into a reviewed explicit import. Its module writes would be rejected by readOnlyPkgs.
This is an evaluation optimization opportunity, not an identified runtime bug or proven performance gain. A larger abstraction may cost more maintenance than it saves with four hosts. Historical relevance: the read-only module received cross-compilation fix 196f6a812b310e3179afcf48bf2907853246dcad on 2025-06-12; f2640ee208003ca7102cbda97740b07871fa7635 on 2025-10-25 changed top-level splicing. Avoid old snippets overriding _module.args.pkgs in NixOS without the supported interface. Nixpkgs' perSystem package memoization itself was improved by b78a8c9109b481e559c7b350695e671b3fbc37db on 2025-07-07, so the local memoization comment is useful but does not cover host instances.

10. Optional future work: use upstream hardware.facter only when a real target report is available.
Locations: devices/nixos-{build01,desktop,ext}/hardware.nix:8-30 and hostPlatform entries in flake.nix.
NixOS Facter entered nixpkgs in October 2025 (b7f40d25ebe0e89abb8d557e162592e9088f240e); boot/storage, CPU firmware, graphics, and networking detection followed in ab49e37a022de924b83b600371dd89d5135ca23c, cb883c36e3ee6551fa2b67c481a58d1186e83c38, ddf53abd21a45a2f3ba3e909c8ef7125ae991198, and 79d683f4ad85450287f8e723afc09c191d5839b5. It requires a report captured on the actual host, and can enable networking, graphics, Bluetooth, and other services. Avoid a blind migration for headless builders or the specialized Orin. Keep desktop's measured 5.2GHz stability cap, NVIDIA package/profiling policy, and network identity explicit.
Current microcode defaults remain false, and enableAllFirmware defaults false: the existing true settings are intentional behavior, not old defaults that can be deleted. stateVersion 24.05/25.05 likewise encodes installation compatibility and must not be advanced as a cleanup.

Recommended implementation order
First remove the obsolete desktop mount workaround and Orin's duplicated CUDA block; compare the affected evaluated options. Next introduce one common fleet profile and common SOPS/Disko declarations, verifying imported service enablement, disk definitions, filesystem options, root snapshot hooks, and stateVersion remain unchanged for all four configs. Then centralize only the already-existing pure host metadata. Keep optional changes (direnv shell integration, nil downgrade to packaged release, readOnlyPkgs, facter) as separate reviewable changes with clear behavior/measurement. No modifications from this audit have been made to the repository.
