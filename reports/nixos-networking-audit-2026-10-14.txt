MAIN RESULT
bpftune makes several static buffer/backlog ceilings unnecessary as permanent
tuning, but does not replace the entire sysctl block. On desktop and ext it is
actually active, fully supported, and already exceeds the static 16 MiB TCP limits.
The higher-priority simplification is the repeated physical-interface setup:
both live hosts set the same MAC on two different Ethernet interfaces, install
three default routes, and emit DHCP-server reservations without running a DHCP
server on that network.

6. Exact bpftune constraints and why indiscriminate sysctl removal is inappropriate
   TCP max growth rejects proposed values >=2147483647 bytes. At default
   learning rate 4, increases/decreases are 25%; rates 0..4 use shifts 6..2, i.e.
   1/64..1/4 (some source comments misdescribe the smallest percentage).
   TCP growth is requested near full (typically>=75% of configured ceiling),
   skips locked receive buffers and low-memory state, and latency correlation
   >0.75 after at least 10 samples changes growth into a 25% decrease, stopping
   if new max would be<=default. This is event-driven reactive tuning.
   UDP rmem range 8192..268435456; BPF growth rejects >=upper bound. Socket drops
   must occur close enough to rmem_max/default to justify changing that limit.
   Explicitly locked default buffers do not cause rmem_default growth, and
   changing a global default does not resize all already-existing sockets.
   UDP init returns -ENOTSUP below full/normal BPF support; legacy mode does NOT
   supply this tuner. Full 9 tuners verified only on live desktop/ext.
   netdev budget uses signed-int guard and caps netdev_budget_usecs 50000 us;
   scheduling wait/run correlation can reduce budget. Flow CPU bitmask handler
   acts only for CPU<64. These settings are not present in the repo but are
   automatically managed, so extra static tuning of them is unnecessary.
   TCP-connection tuner starts aggregate learning at 4 connections per destination
   route/gateway, switches to BBR above retransmission ratio 1/64 (~1.56%), and
   performs exploratory choices for 5% of decisions. Not an always-BBR policy.

   IMPORTANT VERSION-SPECIFIC SOURCE INFERENCE (not reproduced under pressure):
   In tcp_buffer_tuner.bpf.c:94-105 and udp_buffer_tuner.bpf.c:95-107, the code
   sets new exhaustion limit=min(available_pages>>2,grow(old_limit)), then checks
   new_limit<=available_pages>>2 and returns before its documented buffer-shrink
   fallback. The condition appears necessarily true; this means documented
   memory-exhaustion shrink protection should not be assumed guaranteed in 0.4-2.
   UDP unreachable fallback also labels both rmem reductions RMEM_MAX. Recommend
   an upstream source review/fix rather than stressing live build hosts to test.
   Actual source tests use min/pressure growth thresholds 6.25%/12.5% of startup
   free-buffer-page estimate; these are grow conditions, not strict clamps (one
   growth can overshoot). Aggregate max is capped 25%. The manpage's 6%/9% wording
   is not an exact description of current implementation.

7. Boot settings do NOT disable bpftune at boot; later writes can disable tuners.
   Upstream unit After=systemd-sysctl.service network.target. It sees boot sysctls
   as initial values. Desktop today 16 MiB->596046446 (~568 MiB) receive ceiling;
   ext receive 305175781 (~291 MiB), send 125000000. Min/default values unchanged.
   All 9 tuners active on both; no Oct 14 logs matched disabling/error/failed.
   bpftune sysctl tuner detects subsequent administrator/systemd writes and
   disables the associated WHOLE tuner for that namespace until restart. A
   later config switch that reapplies a managed value may therefore stop tuning,
   even if the bpftune service still appears active. This audit did not provoke
   that behavior. Monitor read-only bpftune -q tuners/jstatus after future switches.

8. DNS and networkd cleanup
   modules/networking.nix:12-14 comment says only primary router DHCP offers are
   accepted. UseDNS=false only ignores DHCPv4 DNS; it does NOT filter DHCP
   offers, gateways or leases. If offer filtering remains needed on Orin,
   dhcpV4Config.AllowList is the current option (with RapidCommit caveat). First
   decide whether comment is stale; do not silently add filtering globally.
   IPv6 DHCP/RA DNS acceptance is separate and remains unspecified.
   :19-35 public Cloudflare+DNS64 addresses are deliberate provider/transport
   policy, not something bpftune can remove. Both NAT64 addresses are still
   listed by nat64.net today. Mixing ordinary DNS and DNS64 changes answers
   between providers; on existing dual-stack LAN, scope DNS64 to an actual IPv6-
   only use case if it is unnecessary. Strict DoT needs resolver support and
   valid TLS identities; support of the NAT64 endpoints was not tested here.
   The Hetzner authoritative DNSSEC comment does not alone explain downgrading
   validation by Cloudflare/nat64 recursive resolvers. Keep allow-downgrade only
   as an explicit compatibility policy; no change recommended without reviewing
   resolved behavior for actual domains.
   :113-114 and :123: useNetworkd=true already enables systemd.network.enable.
   Removing duplicate :123 is a trivial option cleanup. useDHCP=false remains
   appropriate with explicit per-link DHCP policy. Alternatively use only native
   systemd.network config plus disabled legacy DHCP, but audit all imports first.
   :17 RequiredForOnline=no and :124 wait-online.enable=false overlap today;
   former still records per-link intent if waiting is re-enabled. Do not treat
   either as performance tuning or blindly remove waiting policy on build hosts.
