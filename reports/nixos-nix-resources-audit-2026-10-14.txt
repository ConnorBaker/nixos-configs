1. Strongest substantive default-change candidate: obsolete oversized download
   buffer workaround. modules/nix/default.nix:128-131.
   Setting=256 MiB; pinned Nix default=1 MiB, filetransfer.hh:149-157.
   The comment cites PR11171, merged 2024-07-29, which raised the buffer to
   64 MiB to work around curl transfers stalling while the sink unpacked.
   Upstream 4307420c4473 (2025-11-22) replaced shared-thread stalls with
   transfer pause/resume and continued other multiplexed downloads.
   Upstream a2d6a69d45d8 (same date) explicitly says that fix removes the
   root cause, and reduces the default from 64 MiB to 1 MiB.
   Recommendation: remove the 256 MiB override and stale PR11171 comment,
   or stage its removal with representative substitution/fetch observation.
   This is an upstream-fix-backed tuning simplification, not a claimed local
   benchmark win. Buffers grow on demand, not an immediate 256 MiB reservation.
   With 32 HTTP connections, larger buffers can overlap: the configured
   threshold budget could approach 8 GiB, versus 32 MiB at defaults, if all
   32 qualifying buffers filled. That is not guaranteed allocation or residency.
   Connection count is not proof that 32 buffers fill. Nix can exceed the
   threshold slightly for sink/decompression callbacks.

Workload tuning decisions: review separately; do not silently reset to defaults

5. Memory/parallelism budget is spread across three independently meaningful
   knobs. modules/nix/default.nix:152 max-jobs 3; modules/services/tribuchet.nix:
   37 agents 3 and 41 max-jobs 3; local cores inherits 0 (all available CPU cores).
   The direct builder maxJobs 3 at modules/nix/default.nix:45 also controls
   client-issued remote jobs. None of these is a CPU/memory quota. Multiple
   jobs can each run make/GHC with full core count and compete with direct
   daemon jobs and remote agent jobs. autoUID+cgroups provide accounting and
   cleanup, but do not themselves set CPUQuota, MemoryHigh or MemoryMax.
   Recommendation: retain max-jobs 3 (local 1d54f7a, 2025-10-05 explicitly
   reduced it to avoid test failures), then assess host specific cores and
   separate CPU/GPU workload concurrency from build logs/PSI during real
   workloads. Avoid max-jobs="auto" restoration: NixOS default would mean
   one concurrent build per logical CPU, excessive for compiler/CUDA jobs.
   Do not assume agents 3 means 3 times 3 active builds without reading the worker
   scheduler contract. Sharing the literal 3 could reduce drift but could
   wrongly couple independent scheduling controls; use named roles if
   centralizing values. Offline build01/Orin need no runtime probing.

6. nar-buffer-size 1 GiB is still a deliberate 32x-default memory/storage tradeoff,
   not a removed workaround. modules/nix/default.nix:155. Pinned Nix defaults
   to 32 MiB; local-store.cc:1256-1289 buffers each addToStoreFromDump input
   before spilling larger inputs to a temporary path in the Nix store.
   Raising it avoids temporary writes for medium/large inputs but holds
   potentially large per-operation strings. Concurrency of client imports,
   evaluation/IFD and substitution can add to compiler memory demand.
   max-substitution-jobs 32 and http-connections 32 remain above defaults 16/25.
   Recommendation: profile peak Nix RSS and import/fetch throughput using
   existing workloads, then consider 32-128 MiB or host specific budgets. Do
   not present 32*1 GiB as guaranteed active memory: paths/imports use different
   APIs and only actual concurrent qualifying operations allocate buffers.
   Neither CUDA archive size nor large RAM alone establishes that 1 GiB is
   beneficial now. No local performance benchmark performed.
   https://github.com/NixOS/nix/blob/a9f38ea0ee89f550616f342386f45e896f4abd18/src/libstore/include/nix/store/local-settings.hh#L268
   https://github.com/NixOS/nix/blob/a9f38ea0ee89f550616f342386f45e896f4abd18/src/libstore/local-store.cc#L1256

7. Zram 400% with no writeback is logical capacity, not guaranteed extra RAM.
   modules/zram.nix:19-21. NixOS default memoryPercent 50; memoryMax is a
   logical disksize cap too, NOT zram's physical mem_limit. 400% was deliberately
   raised in local 365ce7c (2024-03-21). Current desktop read-only sample:
   ~94 GiB RAM, ~376 GiB zram disksize; 0.82 GiB logical pages use 0.24 GiB physical RAM,
   ratio ~3.34 including overhead, far below device fill. This snapshot does
   not characterize compilation peak compressibility or prove 400% unsafe.
   Track orig_data_size/mem_used_total/mem_used_max and memory PSI; lower
   logical capacity or add backing only after evidence. Avoid assuming
   setting memoryMax limits resident RAM. Zram writeback on ZFS needs its own
   design review; no writeback or pool change recommended automatically.
   https://docs.kernel.org/admin-guide/blockdev/zram.html
   https://github.com/NixOS/nixpkgs/commit/c2ecb970df59

8. vm.max_map_count 2147483642 is an extreme inherited application limit.
   modules/zram.nix:10. NixOS already defaults to 1048576, in both 23.11 and
   current pins. The larger value does not preallocate mappings, but no
   compiler/GHC/CUDA evidence here needs ~2 billion VMAs. Recommendation:
   remove only if no known application exceeds 1 million mappings; this is
   application compatibility policy, not a performance optimization.
   https://github.com/NixOS/nixpkgs/blob/7fd4004d0511991fff3a0524856a9be09e28c5f0/nixos/modules/config/sysctl.nix#L115

9. Dirty watermarks and aggressive swap choices have distinct purposes.
   modules/zram.nix:5-13: watermarks 125/0, page-cluster 0, swappiness 190,
   dirty ratio 80/background 50 are explicit tuning, not current NixOS defaults.
   The ratios are generic Linux pagecache dirty thresholds, not OpenZFS ARC
   or TXG controls; all these hosts build on ZFS. High thresholds may be
   largely irrelevant to ZFS writes while affecting Docker/other filesystems.
   swappiness 190 is permitted and can make sense with fast compressed swap;
   Linux docs explicitly allow >100 for zram. It still depends on relative
   filesystem versus swap IO cost, and compilation imposes compression CPU cost.
   Recommendation: separate dirty-writeback settings into storage or workload
   policy and retain zram-specific settings pending workload measurements.
   Do not bundle a reset of 190 to 60 with safe boilerplate cleanup.
   https://docs.kernel.org/admin-guide/sysctl/vm.html#swappiness
   https://docs.kernel.org/admin-guide/sysctl/vm.html#dirty-background-ratio
